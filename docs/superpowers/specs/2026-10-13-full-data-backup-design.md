# YUTORI 全データバックアップ・復元 設計書

## 1. 目的

YUTORI の端末故障対策と、別端末へのデータ移行を可能にする。ユーザーは初回だけ保存先を指定し、その後はヘッダーのボタンから同じバックアップファイルを更新できる。バックアップから復元した場合は、テスト、設定、名簿、答案、採点途中の状態、採点結果を含め、バックアップ作成時点の YUTORI を再現する。

## 2. 成功条件

- 初回のバックアップでは、ユーザーが保存先とファイル名を指定できる。
- 2 回目以降はヘッダーの「バックアップ保存」ボタンで、同じファイルを上書きできる。
- Chrome が保存権限を再確認する場合でも、保存先を選び直す必要はない。
- バックアップには YUTORI が所有する全データと、読み込んだ PDF・ページ画像が含まれる。
- バックアップを別端末へ移し、現在の YUTORI データを全置換して復元できる。
- 復元前には現在のデータを別の安全用バックアップへ保存し、それに成功しなければ全置換を開始しない。
- 破損、不完全、非対応のバックアップは現在データを変更せず拒否する。
- MITORI など、同一オリジン上の別アプリのデータを取得・変更しない。

## 3. 対応環境

正式対応環境は Chromebook／Windows 上の現在の Chrome と Edge とする。File System Access API に対応する環境では、最初に選択したファイルのハンドルを端末内へ保存し、次回以降の上書きに再利用する。

ブラウザ再起動後などに保存権限が `prompt` に戻った場合は、バックアップボタンを押した時点で上書き許可を求める。これは保存先の再選択ではない。

保存先は利用端末に応じて次を標準パターンとする。

- 学校管理の Chromebook: Google ドライブを通常の保存先とする。学校の管理設定で USB が全面的に無効化されている前提とし、YUTORI から USB の利用や制限解除を試みない。
- Windows など学校の Chromebook 以外の端末: Google ドライブの同期領域、または OS から書き込み可能な USB メモリを選択できる。

Google ドライブへ保存した場合、YUTORI が成功として確認する範囲は、選択したファイルへの書き込みと読み戻し検証までとする。Google ドライブのクラウド同期完了は OS・Google ドライブ側の処理であり、YUTORI の完了表示には含めない。別端末で直ちに利用する場合は、Google ドライブ側の同期完了を確認するよう案内する。

記憶した保存先が未接続、削除済み、移動済み、または書き込み不可の場合はバックアップを中止し、保存先の再接続または再選択を案内する。YUTORI が自動的に端末内のダウンロード領域へ保存先を切り替えることはしない。

Safari など File System Access API 非対応環境では、同じファイルへの継続的な上書きは行わず、毎回バックアップファイルをダウンロードする予備方式へ切り替える。復元用ファイルの選択は通常のファイル入力でも利用できる。

## 4. 対象範囲

### 4.1 バックアップ対象

- 作成済み・作成途中のテスト
- 学年、教科、クラス、名簿などの設定
- 採点途中・採点済みのセッション
- 得点、正誤、正答率、結果出力に関するデータ
- 採点パレットと YUTORI 内の表示設定
- `YUTORI_DB` の全オブジェクトストア
  - `pdfFiles`: 読み込んだ元 PDF
  - `pdfPages`: PDF から生成した各ページ画像とメタデータ
  - 将来 `YUTORI_DB` に追加される YUTORI 所有ストア
- YUTORI が所有する localStorage キー
  - `yutori_` を接頭辞とするキー
  - 明示的な互換キー一覧に登録された旧形式の YUTORI キー

### 4.2 バックアップ対象外

- MITORI など別アプリの localStorage・IndexedDB
- バックアップ先のファイルハンドル
- 端末固有の保存権限
- バックアップ処理中の一時データ、復元ステージ、復元ジャーナル
- ブラウザキャッシュと Service Worker のキャッシュ

### 4.3 今回行わないこと

- 自動・定期バックアップ
- Google Drive API 等を利用したクラウド同期
- 2 台の端末で変更したデータの統合・競合解決
- バックアップの世代管理
- パスワードによる暗号化

別端末間の利用は、バックアップファイルを手動で移動し、移動先で全置換復元する方式とする。

## 5. ユーザーインターフェース

### 5.1 ヘッダー

ホーム・設定ボタンの近くに「バックアップ保存」ボタンを追加する。

- 初回クリック: 保存先選択を開き、初期ファイル名 `YUTORI_全データバックアップ.yutori` を提案する。
- 2 回目以降: 記憶したファイルへ上書きする。
- 保存権限が失効している場合: 同じファイルへの上書き許可だけを求める。
- 保存中: ボタンを処理中表示にし、二重実行を防ぐ。
- 成功時: 完了通知と最終保存日時を更新する。
- 失敗時: 最終保存日時を更新せず、再試行可能なエラーを表示する。

マウスカーソルを合わせたときとキーボードフォーカス時には、次の情報をツールチップで表示する。

- 最終バックアップ日時
- 保存先ファイル名
- 未作成の場合は「バックアップはまだ作成されていません」

完全なファイルパスは、ブラウザの安全仕様上表示しない。

### 5.2 設定画面

設定メニューに「バックアップ設定」を追加する。

- 最終成功日時
- バックアップファイル名
- 直近のバックアップ容量
- 「今すぐバックアップ」
- 「保存先を変更」
- 「バックアップから復元」
- 学校の Chromebook では Google ドライブ、その他の端末では Google ドライブの同期領域または USB など、端末故障後も利用できる場所を推奨する案内

復元は破壊的操作のため、ヘッダーには置かない。

### 5.3 進捗表示

バックアップ・復元中はモーダルで以下を表示する。

- 現在の段階（確認、収集、圧縮、保存、検証、復元など）
- 完了件数／総件数
- 可能な場合は処理済み容量／総容量
- キャンセル可能な段階ではキャンセルボタン

書き込み開始後など、安全に中断できない短い段階ではキャンセルを無効化する。

## 6. バックアップファイル

### 6.1 形式

拡張子は `.yutori` とし、単一の圧縮ストリームとして保存する。内部は将来の互換性と大容量処理のため、以下を持つフレーム形式とする。

- 固定マジック値: YUTORI バックアップであることを識別
- バックアップ形式バージョン
- マニフェスト
- localStorage レコード
- IndexedDB レコードとバイナリデータ
- 完了フレーム
- レコードまたはチャンク単位の破損検査情報

マニフェストには少なくとも以下を含める。

- 形式バージョン
- 作成日時
- 作成元の YUTORI バージョン
- データ分類ごとの件数
- 元 PDF 数、ページ画像数
- 非圧縮時の概算容量
- 各 IndexedDB ストアの名前とスキーマ情報

バイナリは一定サイズのチャンクとして順次読み書きし、全 PDF・画像を一度にメモリへ保持しない。Chrome／Edge のネイティブ圧縮ストリームを使用し、処理中のメモリ使用量をデータ総量ではなくチャンクサイズに近い範囲へ抑える。

### 6.2 互換性

- 読み込み側は形式バージョンを確認する。
- 同一形式の古い YUTORI バージョンからの復元を受け入れる。
- 将来形式が変わった場合は、バージョン別の読み込み処理または移行処理を追加できる構造にする。
- 現在のアプリが理解できない新しい形式は、現在データを変更せず拒否する。

## 7. 内部コンポーネント

バックアップ機能を、既存の採点・PDF処理から分離した次の責務に分ける。現行アプリは単一 HTML を中心としているため、初回実装では同じファイル内でも明確なモジュール境界を持たせる。

### 7.1 BackupDestinationStore

別の IndexedDB `YUTORI_BACKUP_META` に以下を保存する。

- 主バックアップの `FileSystemFileHandle`
- ファイル名
- 最終成功日時と容量
- 復元ジャーナル
- 復元中かどうかを示す状態

このデータベース自体はバックアップ対象に含めない。別端末では主バックアップの保存先を改めて設定する。

### 7.2 YutoriDataRegistry

YUTORI 所有データを列挙する唯一の定義元とする。

- localStorage の接頭辞と互換キー
- 対象 IndexedDB 名
- バックアップ対象外のシステムキー
- 件数集計と概要表示の分類

同一オリジン上の別アプリのデータ混入をこの境界で防ぐ。

### 7.3 BackupArchiveWriter / BackupArchiveReader

- ストリーミング形式の書き出し・読み込み
- 圧縮・展開
- マニフェスト生成・検証
- 破損検査
- 形式バージョン判定

UI と保存先 API には依存させず、テスト可能な入力・出力インターフェースを持つ。

### 7.4 BackupCoordinator

- 実行中の YUTORI 保存処理が終了するまで待機
- バックアップ中の新しい変更操作を一時停止
- 保存先権限の確認
- 進捗とキャンセルの管理
- 保存後の読み戻し検証
- 最終成功情報の更新

### 7.5 RestoreCoordinator

- 復元候補の完全検査とステージング
- 内容概要の表示
- 復元前安全バックアップの強制
- 全置換と復元ジャーナルの管理
- 失敗時のロールバック
- 再読み込み後の件数照合

## 8. バックアップ処理の流れ

1. 二重実行を防ぎ、進行中の PDF 取込・採点保存などが終了するまで待つ。
2. 初回は保存先を選び、以後は記憶したハンドルを取得する。
3. `queryPermission()` を確認し、必要な場合だけユーザー操作内で `requestPermission()` を行う。
4. localStorage の対象キーをスナップショットする。
5. `YUTORI_DB` の対象ストアを読み取り専用トランザクションで列挙する。
6. マニフェストと各レコードを圧縮しながら保存先へ順次書き込む。
7. 書き込みを正常終了させる。
8. 保存したファイルを読み戻し、形式、完了フレーム、件数、破損検査情報を検証する。
9. 検証成功時だけ最終成功日時・容量・ファイル名を更新し、完了通知を出す。

失敗時は書き込みを中止し、以前の最終成功情報を維持する。ブラウザが提供する安全な一時書き込みと確定処理を利用し、完了前の内容を正常なバックアップとして扱わない。

## 9. 復元処理の流れ

### 9.1 検査と確認

1. ユーザーが `.yutori` ファイルを選ぶ。
2. ファイルを一時復元領域へ順次展開する。
3. マジック値、形式バージョン、完了フレーム、件数、破損検査情報をすべて検証する。
4. 次の概要を表示する。
   - 作成日時
   - 作成元 YUTORI バージョン
   - テスト数
   - クラス数
   - 採点セッション数
   - 元 PDF 数とページ画像数
   - ファイル容量
5. 非対応・破損・途中で切れたファイルは、この時点で拒否する。

検査とステージングが完了するまで現行データには触れない。

### 9.2 復元前安全バックアップ

現在の YUTORI データを `YUTORI_復元前バックアップ_YYYYMMDD_HHmm.yutori` という初期名で、復元元とは別の安全用ファイルへ保存する。通常のバックアップと同じ読み戻し検証を行う。

安全用バックアップの保存または検証に失敗した場合、全置換は開始しない。

### 9.3 全置換

ユーザーが「現在のデータがすべて置き換わることを確認しました」をチェックした後だけ実行ボタンを有効にする。

全置換は復元ジャーナルを使い、次の順で行う。

1. 現在状態と復元段階をジャーナルへ記録する。
2. ステージング済みの IndexedDB データを適用する。
3. 対象となる現在の YUTORI localStorage キーだけを除去し、復元データを適用する。
4. 適用した件数をマニフェストと照合する。
5. 成功状態を記録してアプリを再読み込みする。
6. 再起動時に再度件数を照合し、成功後にステージとジャーナルを削除する。

途中で失敗した場合は、ジャーナルと退避状態から自動ロールバックする。中断状態で再起動した場合も起動時にジャーナルを検出し、通常画面を開く前にロールバックまたは復元再開を完了させる。自動回復に失敗した場合は通常操作を停止し、保存済みの復元前安全バックアップを使った回復画面を表示する。

復元元に含まれる保存先情報は採用しない。復元後も元端末の主バックアップ先を維持し、別端末では初回バックアップ時に保存先を設定する。

## 10. 同時実行とデータ整合性

- PDF 読込、ページ画像保存、採点セッション保存などの非同期永続化処理を共通の処理追跡へ登録する。
- バックアップ開始時は登録済み処理の完了を待つ。
- スナップショット開始後は、モーダルでデータ変更操作を一時停止する。
- IndexedDB は可能な限り同一読み取りトランザクション内の一貫した状態を列挙する。
- 復元中は YUTORI の通常操作をすべて停止する。
- バックアップ、復元、PDF取込を同時に開始できないよう排他制御する。

## 11. エラー処理

ユーザー向けには、原因と次の行動が分かる日本語を表示する。

- キャンセル: データを変更せず通常画面へ戻る。
- 権限拒否: 保存先は維持し、再度バックアップボタンから許可できるようにする。
- 容量不足: 必要容量の目安と、別の保存先へ変更する案内を出す。
- ファイル使用中: ファイルを閉じて再試行する案内を出す。
- 保存先未接続・利用不可: USB の再接続、Google ドライブへの再接続、または保存先の再選択を案内し、別の場所へ自動保存しない。
- 破損・不完全: 復元を開始せず、別のバックアップを選ぶよう案内する。
- 非対応バージョン: YUTORI の更新が必要であることを案内する。
- 読み戻し検証失敗: 保存成功として扱わず、最終保存日時を更新しない。
- 復元適用失敗: 自動ロールバックを行い、その結果を明示する。

開発者向けの詳細はコンソールへ残すが、答案・名簿などの内容はログへ出さない。

## 12. プライバシーと安全性

バックアップには児童の氏名、答案、採点結果が含まれるため、画面に「個人情報を含みます。学校の管理方針に従った保存先を選んでください」と表示する。

Web アプリからバックアップを外部送信しない。すべてブラウザ内で処理し、ユーザーが選択したファイルへだけ書き込む。初回実装では暗号化を行わないため、その点も設定画面で明示する。

## 13. テスト方針

### 13.1 単体テスト

- 対象 localStorage キーだけを列挙し、別アプリのキーを除外する。
- Blob、File、ArrayBuffer、Date を含む IndexedDB レコードを往復変換できる。
- 複数チャンクに分かれる大きなバイナリを復元できる。
- マニフェスト件数と実データ件数を照合できる。
- 1 バイト改変、途中切断、完了フレーム欠落を検出する。
- 未知の形式バージョンを拒否する。
- 保存先メタデータをバックアップへ含めない。
- 復元時に現在の YUTORI キーだけを置換する。

### 13.2 統合テスト

- 初回保存、同一ファイルへの上書き、保存先変更。
- 権限が `granted`、`prompt`、`denied` の各場合。
- 途中の書き込み失敗と容量不足。
- 安全用バックアップ失敗時に復元が開始されない。
- localStorage と `pdfFiles`／`pdfPages` を含む完全な往復復元。
- 復元途中の疑似中断後、起動時にロールバックできる。
- MITORI 相当のダミーキーが変更されない。
- File System Access API 非対応時のダウンロード方式。

### 13.3 実機確認

- Chromebook Chrome と Windows Chrome／Edge。
- ブラウザ再起動後の権限再確認。
- 学校管理 Chromebook から Google ドライブへの保存と上書き。
- Windows など別端末から、書き込み可能な USB メモリへの保存と上書き。
- Google ドライブ未接続、USB 取り外し時に自動で別の保存先へ切り替わらないこと。
- 複数の答案 PDF とページ画像を含む大容量データ。
- 別端末へファイルを移した全置換復元。
- ツールチップ、キーボード操作、タッチ端末の設定画面表示。

## 14. 受け入れ基準

1. 初回保存後にブラウザを再起動しても、保存先を選び直さず同じファイルへ更新できる。権限再確認は許容する。
2. バックアップボタンのツールチップと設定画面に、正しい最終成功日時とファイル名が表示される。
3. テスト、名簿、採点途中、採点結果、元 PDF、ページ画像がバックアップ前後で一致する。
4. 別アプリのストレージはバックアップにも全置換にも含まれない。
5. 破損したファイルでは復元が開始されない。
6. 復元前安全バックアップが検証済みでなければ、全置換ボタンを実行できない。
7. 全置換中の失敗・再起動から、現在データを自動回復できるか、安全用バックアップから回復できる状態を保つ。
8. 大容量データでも全内容を同時にメモリへ載せず処理できる。
9. 正式対応ブラウザでは同一ファイルへの上書き、非対応ブラウザでは毎回ダウンロードが動作する。
